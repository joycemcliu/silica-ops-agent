## Symptoms

- One render item, such as an AmberSky trailer, repeatedly reports `AE log timeout` while other templates render on the same computer.
- MFR ON crashes, closes the AE connection, or stops reporting progress. MFR OFF can complete the same project.
- Native `aerender` may print `An existing connection was forcibly closed by the remote host.` and still return exit code zero.

Anti-anchoring: a timeout alone does not prove slow rendering; a zero exit code does not prove a valid video. An old timestamp alone does not prove an invalid template. A historical effect-crash file does not identify the current failure. A large offset from an exported function name does not establish the private faulting function.

## Triage (read-only, in order)

These are parameterized forms of checks used in the source incident. Use approved environment access; confirm the renderer's actual interactive context before interpreting a headless reproduction.

1. Inspect current native process context and retained output logs:

   ```powershell
   Get-CimInstance Win32_Process | Where-Object { $_.Name -match '^(aerender[.]exe|AfterFX[.]com|AfterFX[.]exe)$' } | Select-Object ProcessId,Name,SessionId,CommandLine
   Get-Content '<stdout-log>' | Select-String '^aerender ERROR'
   Get-Content '<stdout-log>' -Tail 12 | Select-String 'PROGRESS:\s+\d+:\d+:\d+:\d+\s+\((\d+)\)'
   ```

   Bad: native error/abrupt process disappearance or repeated unchanged progress. Good: advancing progress and no native fatal error, followed by output validation. A process in a different desktop session is a different execution context, not a valid comparison by itself.

2. Validate a claimed successful output independently:

   ```powershell
   & '<ffprobe-path>' -v error -count_frames -show_entries 'stream=codec_type,codec_name,width,height,avg_frame_rate,duration,nb_read_frames:format=duration,size' -of json '<output-file>'
   & '<ffmpeg-path>' -hide_banner -nostdin -v error -i '<output-file>' -f null NUL
   ```

   Bad: empty/unreadable output, unexpected frame count, or decode errors. Good: expected composition frame count and complete decoding. These checks do not establish picture/audio equivalence.

3. Inspect the generated project's resolved `fileReference.fullpath` values and the generating code (`render.go` → `AETmplData.generateProject` → `.Path`). Compare the generated file with the template after resolving its actions.

   Bad: missing/wrong media paths, or preserved import records that disagree with the actual referenced files. Good: paths resolve to intended media and the generated bytes differ only as expected. A path replacement can be correct while other serialized metadata remains inherited.

4. For the verified record layout only, compare `Item.Pin.sspc.bdata[236:244]` with the referenced file's `LastWriteTimeUtc`. The slice is four big-endian bytes at offsets 118–121, storing whole seconds since the 1904 UTC epoch. Use `Get-Item -LiteralPath '<resolved-media>'` and inspect `LastWriteTimeUtc`. Image-sequence references can point to directories.

   Bad: a mismatch identifies a candidate import-refresh trigger. Good: matching timestamps reduce this hypothesis but do not rule out other native AE failures. Compare every changed byte in native-resaved records: `sspc` also contains media properties; copying the entire record is not a timestamp-only experiment.

5. Preserve new native dumps before another AE launch removes them. Correlate creation time, process/run ownership, native module and actual unwound stack. Source-incident analysis used LLDB with matching PE modules. An unmatched old dump, raw address scan, or nearest-export label alone is weak evidence.

## Likely causes

| Cause                                                              | Evidence that confirms                                                                                           | Evidence that rules out                                                                                                   |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| MFR footage-change/import-state refresh issue                      | Strict mtime-only copies succeed while unchanged copies fail; new native importer/render-GUID/MFR stack evidence | Matching metadata still fails under comparable fresh runs; investigate other native failures                              |
| GUID refresh alone is sufficient                                   | A GUID-only controlled variant consistently succeeds                                                             | GUID-only variants failed while timestamp-only variants preserved original GUIDs and succeeded in the source incident     |
| Selected effects are necessary to trigger the failure              | Removing the selected effects consistently removes the failure                                                   | Combined removal of Lumetri, Set Matte and Color Key still failed in the source incident                                  |
| Hardware decoding or tested source chroma format is the sole cause | Only changing that factor consistently removes the failure                                                       | Decoder-off and tested in-game 4:2:0 normalization variants still failed; this does not rule out every decoder/media path |
| NAS access is the sole cause                                       | Failure follows remote access exclusively                                                                        | Locally copied materials still failed; NAS access was not necessary for reproduction                                      |

The alternative-engine trial also stalled, so a downgrade fix was not established. Its output format differed; that attempt does not prove the same internal defect exists in both engines.

## Remediation (HUMAN executes; agent never runs)

1. Run approved controlled experiments on immutable copies in the real renderer context. Keep engine, footage, effects, MFR CPU allowance, memory settings and output format comparable. Change one field group at a time. **Risk:** render load and stale process trees. **Guard/backup:** hash originals, use unique output directories and record exact arguments. **Rollback:** stop only a process tree whose executable and command line identify the owned experiment; remove only its temporary task.
2. Use a native AE refresh/relink/save on a copy to inspect full import-record changes. A strict timestamp-only diagnostic variant is a separate experiment, restricted to the verified record layout and actual resolved-file mtimes. **Risk:** accidental media-property changes or unsupported private-layout edits. **Guard/backup:** preserve source bytes and perform field-level diffs. **Rollback:** return to the untouched source copy; do not overwrite shared experience content during diagnosis.
3. For a runtime timestamp helper, deploy a compatible renderer before publishing converted external templates. `AEFootageMTime` resolves through `.Path` and uses actual filesystem mtime; it must not use the current clock. **Risk:** older consumers cannot execute the new helper, and a different record layout may encode metadata differently. **Guard/backup:** preserve prior renderer/content versions, use the converter's separate output and verify byte preservation. **Rollback:** restore unconverted content before reverting to an incompatible renderer. Stage fresh-session renders before broader publication.

## Validation checklist

Machine checks:

- [ ] Each referenced file/directory is the intended resolved input; generated timestamps match its whole-second modification time.
- [ ] Repeated comparable runs complete, expected frames are present, and the whole output decodes. Exit code zero alone is insufficient.
- [ ] Compare decoded audio and video with a known-good reference; a high similarity score is not pixel identity or universal correctness.
- [ ] No owned diagnostic task/process remains; source/config hashes and ordinary renderer operation are preserved.

Human checks:

- [ ] Review picture content, framing, timing, transitions and audio on fresh generated sessions.
- [ ] Validate the deployed implementation and content release on the intended engines/hosts. Diagnostic file edits do not establish production recovery.
